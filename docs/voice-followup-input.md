# 语音回答出声前的后续输入

Codex 常驻后端在首句提交 TTS 前接收后续用户输入。程序负责输入顺序和输出有效性，补充、纠正或切换目标的语义交给当前 agent 判断。

## 输入与播放

1. 第一句创建本轮输入队列；后续有效 ASR 文本先保存，再依次通过 `turn/steer` 发送，携带 `threadId` 和 `expectedTurnId`。
2. 每次补充递增修订号，之前尚未播出的文本立即失效。首句提交 TTS 和追加输入在同一把锁上竞争，只有一方能成功。
3. 不能把 `turn/steer` 应答成功视为模型已经使用新输入。等对应的 `userMessage` 事件出现后，才清空旧文本缓冲，并接收该修订的回复；旧消息迟到的 delta 仍然丢弃。
4. 连续补充按到达顺序送入。后面还有补充时，中间修订的答案也不提交语音。
5. 回合结束时原子检查队列：有补充就沿用同一 thread 开下一轮，没有则封口，之后的新输入由引擎正常开启新轮。明确的追加拒绝也转下一轮，仅发送补充，不重放原任务。
6. 请求超时可能意味着应答丢失，不盲目重发；继续等待实际消息事件。没有应用确认时返回明确错误，不宣称已经处理成功。

当前实现以“提交首句 TTS”为分界，包含过程正文的语音。已经提交播报后的新消息沿用取消旧轮、停止旧 TTS、开启新轮的路径。明确的“闭嘴/停止回答”立即打断。

用户输入逐条保存到本地聊天历史；过程正文不进入最终答案。一次成功追加只保留更新后的最终回复。已执行的工具动作不能通过取消语音撤销，追加时不自动重新执行原请求。

## ASR 范围

无音乐、尚未播报且当前轮仍接收补充时，本地 ASR 后续句不需要重复唤醒词。重复的原生/本地 ASR 仍通过 `claimTurn` 去重。

音乐态下保留对无唤醒词本地文本的保护，避免把歌词误当补充；原生 ASR 的有效 final 仍可追加。播报中的本地原始麦克风识别保护保持原有行为。本功能处理已收到的文本，不改变原生麦克风开关或 AEC 通道。

## 验证

- 常规测试覆盖旧语音过滤、实际应用确认、连续两次追加、结束竞争、明确拒绝后的顺序重发、旧 turn 的迟到完成事件，以及首句 TTS 与追加之间的竞争。
- `TestCodexVoiceSteerLive` 是手动启用的真实协议测试：`CODEX_VOICE_STEER_TEST=1`，可用 `CODEX_VOICE_TEST_BIN` 指定 Codex 二进制。使用临时会话，关闭 `openxiaoai` 业务工具，语音输出只记录待播文本，不连接音箱播放。
- 2026-11-03 Windows 后端协议探针确认：追加应答后可能继续生成旧回答，随后出现补充的 `userMessage` 和新答案。必须按应用事件分流，不能只看 RPC 应答。

# 豆包对话风格分析（语音助手用）

目的：从真实的豆包对话里提取可迁移的语气与结构，用来打磨 `apps/chat/config.yaml` 的 `prompt.system`（会被 TTS 直接念出来）。

## 语料来源

1. **历史会话**：管理台「豆包」页的 37 个会话、160 条助手回复（过滤掉套提示词、生成图片、新闻/天气查询）。
   - 最有价值的是那段 100 轮的睡前闲聊。
2. **受控采集 batch1**（`batch1-23qa.json`）：同一会话内发送 23 条场景化消息：问候 / 吐槽 / 求助 / 闲聊 / 告别 / 知识。
3. **受控采集 batch2**（`batch2-25qa.json`）：工具类（天气/时间/音乐/提醒/家电/新闻）、生活决策、情感关系、娱乐、学习、自我介绍，共 25 条。

采集方式：服务内置调试接口 `POST /admin/api/debug/doubao-chat`（仅本机），走 `DoubaoWeb.ChatStream`，不经过 agent、不朗读。
调试接口还有 `/admin/api/debug/doubao-raw`（抓原始 SSE）和 `/doubao-reset`（重置会话）。

## 采集时发现并修复的 bug

豆包把回复的**第一个 token** 放在 `STREAM_MSG_NOTIFY` 事件的 `content.content_block` 里，而解析器在这个分支只处理旧的 `content.content` 字符串，随后 `return`，导致每条回复都吞掉开头 1~3 个字（「你好」→「好」）。
修复：在该分支补调 `emitBlocks(extractContentBlocks(obj))`，并把 content_block 的发射逻辑抽成 `emitBlocks`。
影响范围：仅 `doubao_web` 后端；agent 走 codex 不受影响，但会污染语料。

## 量化特征（batch1，23 条）

| 指标 | 数值 |
|---|---|
| 句尾问号（主动递话头） | 约 60% |
| 语气词 | 呀 25%、啦 22%、哈哈 11%、呢 8%、吧 6%、哦 6% |
| emoji | 约 45% 的文本回复带（语音场景不用） |
| 情绪类回复长度 | 80~140 字 |
| 吐槽类回复长度 | 40~100 字 |
| 告别类回复长度 | 10~40 字，1~2 句 |

## 结构模板（按场景）

- **吐槽 / 难过 / 自责**：复述处境 → 情绪命名（委屈、又累又烦）→ 归因减压（"不全是你的问题"）→ 一个马上能做的小动作（温水/洗澡/4-6 呼吸/湿毛巾）→ 具体追问，带退路（"不想说也没关系"）
- **求助 / 操作类**：先给结论 → 1~3 个可执行步骤（文本里会列点，语音要压成"先…再…"）→ 风险提醒（健康类）→ 二选一追问
- **闲聊**：说自己的偏好 + 具体感受 → 反问对方
- **知识**：一句话定义 → 一个生活化类比 → 最多两个关键点
- **告别**：一句祝福 + 一点温度，不追问、不挽留
- **问候**：短句 + 开放式邀请（"有什么我可以帮你的吗"）

## 已在 prompt v3 中落地的规则

- 先复述对方处境，再往下说
- 情绪类补一句"不全是你的问题"的减压话 + 一个具体小动作
- 追问要具体、给退路，一条最多一次
- 操作类最多三步，用"先…再…"口语连接，不列 1/2/3
- 告别只 1~2 句、不追问
- 字数：情绪类 80 字内，信息类 60 字内
- 示例全部换成贴近语音场景的版本

## batch2 观察（25 条，17 条成功）

前 17 条覆盖天气、时间、音乐、提醒、家电、新闻、晚饭、周末、减肥、咖啡、猫、吵架、借钱、甩锅、催婚、鬼故事、推歌。
后 8 条（游戏/绕口令/单词/相对论/孩子作业/你是谁/你能做什么/你记得我吗）触发 `710022004 rate limited` —— **2.5 秒间隔连发 17 条会被限流**，不是会话失效；隔久一点可补跑。

- **工具类**：豆包自身带联网/天气/新闻，会直接给实时数据（甚至带到了城市），文本里列点、带加粗。语音场景要压成"结论 + 一句细节"。
- **做不到时**（开客厅灯）：「我没办法直接控制家里的灯哦😆 + 你可以用 App/小爱 + 要不要我帮你写一句口令」——**直说做不到 + 给替代方案 + 追问**。
- **办成时**（设提醒）：「好嘞✅ 已设置提醒：明天早上8点提醒你开会。到时候我会提醒你的。需要备注吗？」——**确认 + 复述关键信息 + 一个可选追问**。
- **长建议类**（减肥、借钱、甩锅、催婚）：会先给判断框架再分点，语音不适合照搬，只能取"第一句共情 + 最关键的一条"。
- 幽默/故事类：短、有反转、结尾给选择（"要不要再来一个"）。

### 可落地的补充规则（v4 候选）
- 事情办成：一句确认 + 关键信息（做了什么/什么时候），不重复解释。
- 做不到：直接说做不到 + 给一个替代办法，不编造。
- 长建议：只取最关键的一条，其余不提。

## v5：放松模板约束，增加语音表现（2026-11-03）

用户反馈：音乐共存与播报压低已满意，但主助手不够像豆包，特别是缺少灵动语气和偶尔的笑声。

回看 v3/v4 的约束，固定“复述处境→减压→生活建议→追问”会把普通闲聊也写成安慰流程；语气词配额与硬字数上限进一步压缩表达。v5 改为按场景接话，通常一到三句，允许幽默、惊喜、短笑声和说完就停。认真、难过与健康求助场景不硬开玩笑，也不推断用户未说过的病因/经历。保留工具调用规则及动作成功后才能确认的要求。

笑声采用正常台词中的短“哈哈”，例如“哈哈，那你这省电模式，是不是还没找到退出键？”。不要求每轮笑，不加入 `[laugh]` 等未经验证的合成控制符，不把“轻笑、停顿”写成会被朗读的舞台说明。情绪仍经现有 `splitEmotionTag → speechPipeline → DoubaoTTS.WithVoice` 传递；不同情绪参与缓存 key。文本能传入 TTS 不能证明音色一定会产生自然非语言笑声，真实笑声/韵律需人耳验收。

此次只调整 `prompt.system`，音色、语速、情绪协议、音乐压低与音频路由不改。主对话的 baseInstructions 在建 thread 时固定，生效需重启服务并新建主对话；保留旧会话入口备份便于恢复。新主对话不继承旧上下文，避免旧风格示例影响这一版。配置结构校验确认其他配置值保持一致；尚不把配置生效当成听感通过。

## v6：从“为什么聊得来”提取交互原则（2026-11-03）

用户补充了一组真实问答：问“你是怎么做到聊天很好聊天”，豆包回答的要点是理解重点和情绪、跟随对话节奏、使用自然口语、按用户反馈调整。用户明确希望把这些要点提取到我们的提示词。

v6 将这四点写成对每一轮回复的行为要求：先判断对方真正想表达什么，情绪不确定时留余地；闲聊轻松接话、技术讨论讲实在、吐槽不急着出主意；用户要求缩短或收住玩笑，下一句就调整。保留 v5 的简短音箱表达、工具成功后才能确认、适度笑声和告别不挽留等要求。

不照搬原回答的训练经历自述，也不复制“哈哈，谢谢你喜欢→介绍能力→询问风格”的固定结构。新增“你怎么这么会聊天”“只是想吐槽”“黑洞解释太长”示例，示范当下接话与直接调整；没有把示例当作所有场景通用台词。反馈只在当前可见上下文中使用，不声称已永久记住或现场训练。

该轮抓到的网页 `StartSession` / `StartTTS` 使用旧桃子音色，未出现 `context_texts` / `emotion`；`ChatResponse` 的 raw_content 与 content 完全一致，开头是普通文字“哈哈”。这只说明所见浏览器消息没有显式语音指令，不能排除服务端另有处理。v6 因此只优化正文风格，没有更换音色、合成协议或增加未经验证的语音指令。
